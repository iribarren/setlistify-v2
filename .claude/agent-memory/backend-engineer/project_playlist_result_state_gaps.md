Fixed on `bugfix/playlist-result-state-gaps` (docs/specs/2026-08-24-playlist-result-state-gaps.md):
`NoSetlistCause` (folded from `Playlist::$reportSummary`'s `NO_SETLIST_FOR_BAND` entries) forwarded on
both playlist output DTOs, plus `PlaylistOutput.sourceSetlists` backed by a new nullable `Setlist.url`
column.

**`doctrine:migrations:diff` on this repo currently includes a large amount of pre-existing, unrelated
schema drift** (index drops/recreates on `bands`/`playlist_generation_jobs`/`provider_settings`, id
`GENERATED BY DEFAULT AS IDENTITY` toggles on `setlist_cache`/`setlists`/`songs`, an index rewrite on
`streaming_accounts`, a default drop on `users.backup_codes_hashed`) — confirmed present via
`git stash` on master with zero entity changes. **Do not let `migrations:diff` autogenerate the
migration file for a small change** — it will bundle in all of this. Instead hand-write the migration
with only the intended `ALTER TABLE` statement(s), then verify with a second `migrations:diff` run
that no SQL mentioning your own table/column remains (confirms your mapping now matches the DB,
leaving only the pre-existing baseline drift). `doctrine:schema:validate` will still report `[ERROR]`
after this — that's the baseline, not a sign your migration is wrong.

**A migration must be applied to BOTH the dev and test databases separately** —
`doctrine:migrations:migrate --env=test` is a distinct run from the default (dev) one. Forgetting the
`test` one produces `SQLSTATE[42703]: Undefined column` failures that look like a mapping bug but are
just an unmigrated test DB.

**setlist.fm's setlist-detail payload has its own top-level `url` field**, sibling to `artist.url` and
`venue.url` (which `SetlistNormalizer` already read for `ArtistSearchCandidate`) — easy to miss by
skimming a truncated fixture dump, since the top-level `url` key sits at the very end of the JSON
object, after `sets`/`info`. Always check the *full* fixture file (or `python3 -c "import json;
print(list(d.keys()))"`) before asserting a payload does/doesn't carry a field, not just a `head`.

**[[project_playlist_output_dto_enums]]'s debug:false stale-container-cache gotcha recurred here** —
same fix, `rm -rf var/cache/test var/cache/dev`, needed again after adding a constructor arg to
`PlaylistOutputMapper`/`PlaylistGenerationJobOutputMapper` before the `debug:false` cross-owner-404
tests would pass. Treat it as recurring on every DI-shape change to a heavily-covered service, not a
one-off from that earlier fix.

**`AdminUserActionsTest`'s three tests are order-dependent-flaky against the full suite** (audit-log
row-count assertions off by one when run after certain other test classes, pass cleanly in isolation
and pass on a subsequent full-suite run) — confirmed pre-existing via a clean full-suite rerun with no
code changes in between. Not caused by playlist/setlist changes; don't chase it as a regression from
unrelated work unless it's newly *always*-reproducing.

**Building a value from a lazy-loaded, potentially-null association across two hops
(`PlaylistTrack::getSourceSong()?->getSetlist()->getUrl()`) was accepted as "no new query" for
D-185's `sourceSetlists`**, consistent with the pre-existing pattern where `getSourceBand()->getName()`
already lazy-loads a join in this same mapper. `getSourceSong()` can be null (the FK is
`ON DELETE SET NULL` when a purged setlist's `Song` rows cascade-delete) — that naturally degrades to
`url: null`, which is the honest state for a purged setlist anyway.

See [[project_playlist_output_dto_enums]] for the enum-DTO pass-through convention this fix followed
again (`NoSetlistCause` on both DTOs, never `->value`), and [[project_concert_domain_api]] for the
original debug:false cache-staleness writeup.
